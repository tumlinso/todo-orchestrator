# Todo Orchestrator reference baseline

This baseline records source behavior to inform the standalone Todo Orchestrator redesign. It describes the code at the captured revisions; it does not establish the old package as a new public contract. `retain` means preserve a safety property, `adapt` means preserve its intent while replacing its shape, `isolate` means keep behind an optional importer/provider/host boundary, and `retire` means do not carry the historical behavior into the standalone product.

The primary reference is the standalone package at `/home/tumlinson/skills_dev/todo-orchestrator`, inside the `skills_dev` checkout at `bfa9238985dfeb2368bad076f1cc51bfdadbae92` (`development`). Its `pyproject.toml` names distribution `todo-orchestrator`, version `0.3.0`, imports `todo_orchestrator`, and has a mandatory `mcp[cli]` dependency. The second reference is the vendored copy at `/home/tumlinson/project-control/src/todo_orchestrator`, in Project Control revision `fba161b1dc6ed4399c1a3818071eacdb9b80c17d` (`main`, one commit ahead of `origin/main`). These are separate snapshots: source comparison found differences in `background/worker.py`, `context.py`, `plan.py`, `read_port.py`, `runtime_identity.py`, `service.py`, `workflow/context_fragments.py`, `workflow/lanes.py`, and `workflow/runs.py`; the skill copy alone has `workflow/mcp`, while the Project Control copy alone has package schemas and `workflow/reconcile_cancelled_run.py`. Do not assume a behavior found in one copy is present in the other.

The source inventory and captured SHA-256 values are in [reference-baseline.json](reference-baseline.json). At capture, the Todo source/test paths were clean in both source checkouts. The `skills_dev` checkout already had edits to `.todo-orchestrator/state.snapshot.json`, Todo projections and Todo records, plus an untracked `._AGENTS.md` and Todo record. The Project Control checkout already had unrelated documentation, scripts, application and test edits and was one commit ahead of its remote. Their full status listings are recorded in the JSON. The selected source and test hashes were rechecked after writing these artifacts. No old test suite, service, Project Control runtime, or live authority was executed or changed.

## Disposable fixture descriptions

The old test helper `tests/v2_helpers.py::V2Repo` uses `TemporaryDirectory`, initializes a disposable Git root and points Todo state into a temporary `runtime` directory. Its tests were inspected, not executed. The following descriptions are parity targets for new tests; they are not claims that the new product already passes them.

1. **Atomic event and replay:** create an ephemeral SQLite authority; inject an exception after a domain write but before `Database.mutate` returns; assert the row, revision and event all roll back. Apply one command with a stable request key twice; assert the same durable receipt and no second outcome or semantic revision. Current old-code analogues are the event monotonicity and concurrent pulse tests; generic command replay remains unproven.
2. **Plan no-op and preservation:** compile a small plan with parent, task, frozen interface and required gate; preview then apply, repeat unchanged input, and assert no revision/event change. Omit one declared item and assert the diff explains it without deletion; attempt to weaken active/frozen work and assert refusal. Use only a temporary project database.
3. **Typed cycle witness:** create task → checkpoint, checkpoint produced by another task, and that producer depending on the first task; assert compilation rejects the whole typed cycle and returns a stable witness. Include unknown conditional decisions to prove unresolved branches are not treated as false. This exercises a known gap beyond the old task/task cycle fixture.
4. **Admission race and scope conflict:** two independent processes use one disposable SQLite file and race for one task; exactly one receives a claim, the other gets a typed blocker, with one claim/event. Repeat with disjoint scopes (both may be admitted) and overlapping write scopes (second refused absent a complete isolation proof).
5. **Isolation proof pair:** in an ephemeral Git repository, use two lanes with overlapping paths and isolated worktrees sharing one base plus a separate exclusive integration destination; assert both claims are permitted. Remove or invalidate the integration destination and assert the second claim and any advisory parallel preview are blocked consistently.
6. **Explicit restore:** in a temporary project, write a snapshot and remove the database. Assert ordinary status/read does not initialize or restore. Then authorize a restore proposal bound to project identity, schema and expected authority; reject a mismatched project snapshot and accept an exact one with a durable restore receipt.
7. **Evidence freshness:** pass a verifier over a tracked input at identity H, change the input or acceptance contract before final completion, and assert acceptance is stale/refused while historical evidence remains visible. Re-run verification at H2, then accept and pin the evidence/verifier/source identities.
8. **Child rights and acceptance:** authorize one child under a temporary parent claim; permit nested in-scope write, reject sibling/traversal scope, reject child completion of the parent, and keep a changed child result in `ready_for_acceptance` until parent review. Repeat with a read-only child and assert no changed paths can be reported.
9. **Interrupted dirty attempt:** expire a claim after writing an uncommitted file in the temporary repository and make process liveness unknown. Inspection must not mutate; recovery must quarantine and preserve the file until an authorized, fresh decision reconciles it.

## Evidence limits and open points

- This is source inspection and test-corpus inspection, not runtime qualification. No legacy tests were run, no services were started, no production/live Todo authority state was queried during source qualification, and no legacy file was modified. Project Control development-authority workflow used for this task is separate from this legacy-source inspection.
- `MIGRATION_MAP.md`, `PRODUCT_SPEC.md`, and `DOMAIN_AND_INVARIANTS.md` are proposed design inputs. Their requirements are distinguished here from observed old-code behavior.
- The source map does not prove an exploitable defect from a predicate difference. Every changed safety rule needs a focused new test. In particular, decide exact idempotency receipt scope, strict path-subset semantics, canonical import namespace/plan format, and final evidence freshness policy before freezing those contracts.
- Project Control adapters and cutover tasks in the supplied package are not part of this Todo-only baseline. They do not authorize changes to the active Project Control instance.
